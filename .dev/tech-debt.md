### Keycloak sessions: refresh, sign-out and session lifetime must be fixed before login is enabled
fix: six defects, in the order they will be hit once login is enabled.

1. **Dev has no auth configuration at all.** `envs/dev/stateless/helm/stage/values.yml` in `overture/infra` sets no `NEXT_PUBLIC_AUTH_PROVIDER`, no `NEXT_PUBLIC_KEYCLOAK_*`, and no session or token encryption secrets. With the provider unset, `getConfig()` yields an empty string, so neither auth branch runs and the navbar shows no login control. Secrets belong in a VSO companion, not in the values file.

   **Both encryption secrets must be set explicitly, and both must fail closed.** Set `SESSION_ENCRYPTION_SECRET` and `ACCESSTOKEN_ENCRYPTION_SECRET` in the deployment through VSO. In `global/config.ts` neither may carry a default value, and the application must refuse to start without either, as NextAuth already does for its own key; a default committed to the repository would also breach the project's no-credentials constraint. Test: start the application without each secret in turn and assert it refuses. Severity: high, fix before Keycloak login is enabled in any shared environment.
2. **The Keycloak client and Stage must agree on the client type, decided before login is enabled.** Either confidential, with the secret injected through VSO, or public, with PKCE enabled in `KeycloakProvider` (`checks: ['pkce', 'state']`) and no secret anywhere, including in `refreshAccessToken`. The dev client is defined in `keycloak-configs/clients.tf` and `KeycloakProvider` in `pages/api/auth/[...nextauth].ts`; the two have to be changed together. Once Usher's bridges are in front of the applications Stage calls, the client also needs an audience mapper naming each of them: the controller accepts a token only when its `aud` names the bridge's application, and a missing mapper fails closed, refusing every request.
3. **The refresh can never run.** In the `jwt` callback the refresh sits in the `else` of `if (trigger === 'signIn')`, guarded by `account?.provider === AUTH_PROVIDER.KEYCLOAK`. next-auth passes `account` only on sign-in, so in that branch it is always undefined and the guard is always false. After Keycloak's access-token lifespan (default five minutes) the token expires for good: calls through the protected Keycloak proxy, which the API-token page uses, start failing, while the UI still shows the user signed in, since the Keycloak branch of `pages/_app.tsx` checks only that a session exists. The guard should read `token.account?.provider`. Usher confirmed independently, from next-auth 4.23.1's installed source, that `account` is passed only at sign-in. **It becomes visible to users once Usher's bridges validate tokens:** with five-minute tokens and a one-hour session, a signed-in person would lose access to controlled data five minutes in while their session still looks healthy.
4. **Fixing 3 wakes two defects in code that has never run.** `refreshAccessToken` in `global/utils/keycloakUtils.ts` returns `undefined` on a non-OK response, which the caller spreads into the token as a no-op, so a failed refresh is silent and the dead token stays. And Keycloak's refresh response carries `expires_in`, not `expires_at`, so the stored expiry is never advanced: after the first refresh the old expiry is still in the past and every later session read refreshes again. Recompute `expires_at` from `expires_in`, and on failure end the session rather than keep the stale token. Also refresh one at a time per session: concurrent requests racing on a rotated refresh token can sign the person out, which Usher flagged as a failure seen elsewhere. Land all three of 3 and 4 together.
5. **Sign-out must end the Keycloak session, not only Stage's.** Implement RP-initiated logout in `handleLogout` (`components/UserDropdown.tsx`): `signOut({ redirect: false })`, then send the browser to the realm's `protocol/openid-connect/logout` with `id_token_hint` and `post_logout_redirect_uri`, which Keycloak 18 and later require. The `id_token` is available: it is stored with the account at sign-in and survives refresh, since the refresh spreads the old account first. Register a post-logout redirect URI on the client in `clients.tf`. Test: after signing out, a fresh sign-in must prompt for credentials. Severity: high, fix before Keycloak login is enabled in any shared environment.
6. **Stage's session must not outlive Keycloak's.** Cap NextAuth's `maxAge` at the realm's SSO limits (the standard realm: 30 minutes idle, 10 hours at most), or tie the session's life to refresh succeeding, which fixing 4 makes possible.
standalone: no for 3 and 4, which must land together or the fix introduces the refresh-on-every-read defect; 1 and 2 are infra and client decisions that gate any login at all; 5 needs both Stage code and client configuration
context: found 2026-10-09, preparing for enabling Keycloak login and logout in overture-dev, which runs Keycloak 26.3.3. Read from the code and from next-auth v4's and Keycloak's documented contracts, not executed, since login was not yet configured in dev; the next-auth behaviour behind 3 was since confirmed by Usher from the installed source. Item 6 and the serialization requirement in 4 come from Usher's session-layer rules, recorded in full in `.dev/docs/atlas/roadmap/session-layer.md`. **Under the health-data bar this is not only a Stage concern:** Stage is the first integration target and its auth handling is meant to carry to iMicroSeq afterwards, so these fixes need to land in Stage before its pattern is carried to the application that will handle Indigenous health data.

### The explorer's `filters` URL parameter migrates no legacy links, and validates nothing
fix: two independent defects in the same path, `components/pages/explorer/PageContent.tsx` and `global/hooks/useUrlParamsState.ts`.

- **The legacy-key shim migrates nothing, because its output is never used.** `prepare: (v) => v.replace('"field"', '"fieldName"')` runs inside `useUrlParamsState`, but the hook uses the prepared query only to decide whether to call `router.replace`. The URL it replaces with is built from the unprepared query, and the value it returns is deserialized from the unprepared `currentQuery`. So the shim's output reaches neither the URL nor the SQON handed to Arranger, and no legacy link is migrated at all, not one filter and not all of them.

  **So pre-rename shared links are very likely broken today, not harmless.** Verified by execution at two layers: the current `@overture-stack/sqon` schema rejects a leaf carrying `field` ("content.fieldName expected string, received undefined"), and Arranger's router on current main validates nothing against that schema and compiles a leaf without `fieldName` to a null clause, so a two-filter legacy link becomes `{"bool":{"must":[null,null]}}` where the `fieldName` form becomes a terms query. Not verified: whether the Arranger server actually deployed behind Stage matches main, and what the search engine does with a null clause, either an error or the filter silently dropped. Neither applies the link as its author wrote it.

  The remaining gap is checkable end to end: send the same filter through Stage's proxy to a deployed catalogue in both forms, with the `fieldName` form as the control that proves the query itself is valid. Not done, because the dev cluster was unreachable at the time.

  **Fix the plumbing rather than deleting the shim, and rename structurally.** Parse the value, rename `content.field` to `content.fieldName` on every leaf, then serialize. That replaces the text substitution entirely, which removes a latent first-occurrence defect (`String.prototype.replace` with a string pattern replaces one match, harmless only because the output is currently discarded) and also avoids corrupting a filter whose *value* is the literal string `"field"`, which any text substitution would rewrite. Cover it with a two-filter fixture run through the hook.

  **Migrate before validating.** The schema rejects the legacy key, so validating first would reject every pre-rename link outright instead of repairing it. The order is parse, migrate, validate.

  **None of this transfers to iMS portal-ui.** It runs arranger-components 3.0.7 on the older `@overture-stack/sqon-builder` rather than `@overture-stack/sqon`, against its own deployed server, so its answer depends on that path and was not verified here. Confirmed by iMS Portal UI in its own installed dependencies.
- **The deserialized value must be validated before use.** `deSerialize: (v) => (v ? JSON.parse(v) : null)` passes arbitrary JSON from the URL straight to `setSQON`. Validate the parsed value against the SQON schema at this boundary, so the explorer only ever acts on a well-formed query rather than on whatever a link happens to contain.

  **And malformed input takes the explorer down.** `JSON.parse` on invalid text raises `SyntaxError`, and `deserializeValue` is called in the hook's return statement, so during render rather than in an effect. Nothing guards it: no `try` in the hook or in the `deSerialize` callback, and no error boundary anywhere in the codebase. Stage does have a custom `pages/_error.tsx`, which routes status 500 to `Error500` and anything else to `ClientError`, so the expected result is the explorer replaced wholesale by a generic error page rather than a blank screen, and unusable until someone edits the URL by hand.

  **The failure is client-side, which makes it the undiagnosable case.** The explorer renders only a loader until `useArrangerCatalogues` resolves, and that hook starts with `isLoading: true` and clears it in a client-only effect, so the server never renders `PageContent` and the parse runs only in the browser. The throw should therefore land on `ClientError` and never reach the server's logs: a user report of a broken explorer would have nothing on the server side to find. The gate is verified; the `ClientError` landing is expected from Next.js's top-level handling, not reproduced.

  **That gate is a side effect of catalogue resolution, not an error-handling decision.** Server-rendering the catalogue list later would move the parse onto the server, and the same failure would start surfacing as a logged 500 instead.

  **The realistic trigger needs no adversary.** Long JSON-in-URL links get truncated or mangled when pasted through email or chat, so a colleague sharing an ordinary filtered view is enough. This is an availability problem, not a confidentiality one.

  Fix by catching the parse and falling back to no filters, then migrating legacy keys, then validating the result against `@overture-stack/sqon`'s schema at this boundary. The catch is independent and can land now; the schema validation depends on adopting that package (see the private SQON type entry below).
standalone: yes for catching the parse and for the structural migration, each small with a test; no for schema validation, which wants the SQON package adopted first
context: found 2026-09-30. Spotted and traced by iMS Portal UI in its own copy of this code, while validating claims Stage had sent to SQON about portal-ui; Stage's copy of the hook is identical and was confirmed to behave the same way. **Test the shim through the hook, never on its own:** run in isolation, the function visibly migrates one filter of two, which is true of the function and false of the application, since the hook discards the result. The validation gap came out of the same exchange, from SQON's question about whether already-shared links could carry an empty nested group. iMS Portal UI then traced the parse path in their own code and found it unguarded during render with no error boundaries, and supplied the everyday-trigger reading; the same structure was then confirmed here, including the `_error.tsx` fallback.

**Fixing this here does not fix it anywhere else, and there are at least two copies.** iMS portal-ui carries the identical shim in its own repository and needs its own fix. The code's history suggests there may be more than two. On Stage's main line the shim arrived in 2024 (#208). It appears earlier, in 2023, as part of an already-written `PageContent.tsx` in the root commit of two separate side branches, `paperscrape` and `ch_portal`, which share those exact commits with the DMS UI repository. A migration shim for a renamed key cannot originate in a root commit, so it was carried in from an older codebase not visible from either repository. The old key most likely comes from the unscoped `sqon-builder` package, whose leaf declares `field`, where the scoped `@overture-stack/sqon-builder` and `@overture-stack/sqon` both use `fieldName`; reported by iMS Portal UI from installed type declarations. Arranger confirmed the string appears in none of its commits on any branch, so it did not come from `arranger-components`. Severity is correctness rather than access: under Usher, enforcement lives in the data service, so a dropped or malformed filter cannot widen what a principal can reach, only what a shared link appears to show.

### Three secrets are frozen at import by module-scope `getConfig()` reads, among seven such reads total
fix: move each to the application boundary and pass the value inward, per `AGENTS.md` § Critical constraints ("library/module code must not read from the environment; configuration belongs at the application boundary, passed in as typed parameters"). Take the secret-bearing three first, since their consequence is the worst of the set:

- `global/utils/crypt.ts` (`ACCESSTOKEN_ENCRYPTION_SECRET`)
- `pages/api/auth/[...nextauth].ts` (`KEYCLOAK_CLIENT_SECRET`, `SESSION_ENCRYPTION_SECRET`)
- `global/utils/keycloakUtils.ts` (`KEYCLOAK_CLIENT_SECRET`)

Then the remaining four, which freeze ordinary config: `pages/api/[...proxy].ts` and `pages/api/protected/[...proxy].ts` (the Arranger API target), `global/utils/constants.ts` (Keycloak issuer and token URLs, computed at import), `global/utils/egoTokenUtils.ts` (the EGO public key). Twelve further call sites read config inside function or component bodies and are fine as they are.
standalone: yes; each site is independent and they can be done piecemeal
context: surfaced 2026-09-21 from an atlas page a sibling-portal session left in this repo (`.dev/docs/atlas/system-alert-config.md`), documenting how a module-scope config read froze an alert-banner value at import and made it awkward to test.

**A frozen secret does not take effect when it is rotated**: the process keeps presenting the old credential until it restarts, which is a worse failure than a stale API target and is the reason to sequence those three first. Otherwise practical runtime severity is low, since a deployed pod gets new config through a redeploy anyway, leaving testability (supplying a fixture means resetting module state rather than passing an argument) and the plain gap between a stated critical constraint and the code.

Worth fixing before the alert-banner feature lands rather than after: house style is what a new feature copies, and that atlas page documents the failure this exact pattern produced elsewhere.

**Sweep with both shapes or the count comes out short.** A pattern requiring the variable list and the call on one line silently skips multi-line destructures, where `const {` opens and `} = getConfig();` closes several lines later. Two of the seven are that shape and were missed on the first pass here. Anchor on both, at column zero to separate module scope from in-function reads: `grep -rn "^const .*getConfig()\|^} = getConfig()" --include="*.ts" --include="*.tsx"`.

### `arrangerFetcher.ts` can't be used as `useArrangerConfig`'s `apiFetcher`
fix: two confirmed, compounding gaps, verified directly against Arranger's source (2026-08-11), not hypothetical. (1) The underlying call is `ajax.post(...)`, hardcoded regardless of `args.method`; `useArrangerConfig`'s bootstrap call sends `method: 'GET'`, which would go out as a POST. (2) Bigger blocker: that same bootstrap call passes `url: apiUrl` (deliberately unscoped, since it's the call that confirms catalogue validity in the first place) plus `endpoint: `${catalogue}/introspection`` (manually pre-prefixed). `arrangerFetcher.ts` ignores the `url` argument by design (it must route through this app's own proxy, not Arranger's resolved host, see the git-archaeology section below) and instead rebuilds the URI from a `catalogue` value baked in at fetcher-creation time, producing a double-prefixed, 404ing path (`{proxy}/{catalogue}/{catalogue}/introspection`). Confirmed with Arranger directly: their contract (`url` pre-resolved to include catalogue) is correct and now documents this bootstrap-call exception explicitly; the incompatibility is specific to a proxy-routing fetcher like this one. Fixing this file to handle both would mean detecting an already-catalogue-prefixed `endpoint` before rebuilding the URI, real but non-trivial; not attempted, since resolving `documentType` a different way (below) sidesteps needing it at all.
standalone: yes
context: the routing half of this file's original bug (root cause of the `/api/arranger/graphql/Arranger-ConfigsQuery` 404 diagnosed against the dev multicatalogue server) is fully fixed and unaffected by this: `arrangerFetcher.ts` takes `catalogue` at creation time (passed from `explorer/index.tsx`'s runtime-resolved catalogue, see `resolveArrangerCatalogue.ts`) and builds the proxy path directly from it for every *other* call. `explorer/index.tsx` resolves `documentType` itself from the same `GET /introspection` response it already fetches for catalogue discovery (a `documentType` per catalogue, straight from Arranger's own response shape) rather than passing `customFetcher` through `useArrangerConfig`'s internal path, so this gap is real but currently unreachable in practice, not just deferred.

standalone: yes; independent of the other `arrangerFetcher.ts` entry above, though touches the same file
